# Полевые заметки: обучение и инференс на RTX 5060 Ti 16 GB (Windows)

> Источник: итоговые заметки родственного проекта VoxelCraft-LM на том же
> железе (замороженный бэкбон + LoRA + обучаемые пространственные модули).
> Проверено нами на Qwen3.5-2B — применимость подтверждается точечными замерами
> (см. историю коммитов). Все числа — измеренные, не вычитанные.

## 1. Windows не падает с OOM — он молча тормозит (WDDM spill)

Драйвер WDDM при превышении VRAM переливает аллокации в системную память и
продолжает считать, в 2–4 раза медленнее. Исключения не будет.

Действия (применено в `src/training/trainer.py`):
- на каждом шаге лога печатаются `memory_allocated()` и
  `max_memory_allocated()`;
- превышение потолка (по умолчанию 14.0 GB) помечается прямо в строке лога;
- просадка `it/s` в разы → первым делом смотреть пик памяти.

## 2. Пик памяти определяют логиты, а не модель

Доминирует тензор `[B, S, V]`; у Qwen3.5 словарь **248 320** (крупнее, чем у
Qwen3). Одновременно живут ~3 копии fp32/float32 + исходник bf16:

```
пик ≈ веса(bf16) + градиенты + состояния AdamW + 3 · B · S · V · 4 байта
```

Следствия, встроенные в дефолты тренера:
- рычаги — только B и S, оба линейны; размер модели почти ни при чём;
- длины измерены на корпусе: prompts p100 ≈ 22, code p100 = 565 →
  `max_prompt_tokens=256`, `max_code_tokens=768` (не «2048 на всякий случай»);
- эффективный батч добирается накоплением градиента (бесплатно по памяти);
- **кэш-аллокатор и разноформенные батчи**: свободная паддинг-длина на каждый
  батч создаёт по пулу памяти на форму; под логитами (3·B·S·V·4B каждый) это за
  ~200 шагов надуло reserved до 18.6 GiB на 16-ГБ карте и уронило прогон в
  системную память. Лечение в нашем тренере: бакетизация длин
  (`seq_bucket=128`) + `torch.cuda.empty_cache()` каждые 50 шагов. Проверено:
  reserved плато 11 GiB, сброс до 4.9 GiB, темп стабилен 1.7 it/s;
- fused cross-entropy недоступна (нет Triton на Windows) — планируем без неё.

## 3. Тяжёлый проектор в объём

Развёртка латента в сетку доминирует среди обучаемых параметров. У нас
`Linear(512 → 32·16³) = 67M` (не 268M, как в VoxelCraft с 2048-входом), но на
будущее варианты: сетка 8³ (в 8 раз легче) или низкоранговая проекция
`512 → 256 → 32·16³` (~34M). Сейчас оставлено как есть — лимит вычерпывают
логиты, а не канвас (см. §2).

## 4. Декодирование упирается в CPU-запуски ядер (Windows)

Стоимость запуска одного ядра ~31.8 мкс (норма ~5). Симптом: время шага
декодирования не растёт от batch=1 до 32 (узкое место — хост-диспетч).
`torch.compile` и HF `static` cache недоступны без Triton, **но**
`torch.cuda.CUDAGraph` Triton не требует — ручной захват шага декодирования
даёт кратные ускорения (в их замерах 9.6→67 tok/s при batch=1 и до ~930 tok/s
при batch=32).

Правила захвата (для будущего инференс-ускорителя, ARCHITECTURE.md §7):
- префилл обычный; граф — только для decode-шага с `StaticCache`;
- маска внимания известна заранее (левый паддинг!), между реплеями не трогаем;
- argmax + запись следующего токена + инкремент позиции — внутри графа;
- стоп-токены накапливать на GPU, синхронизация раз в N шагов, иначе EOS
  между проверками теряется и генерация домалывает всю длину;
- на любом сбое захвата — тихий откат на обычный `generate()` с логом причины.

## 5. Неслитая LoRA стоит ~30% на инференсе

Три matmul вместо одного на каждую проекцию. Для оценки/генерации датасетов —
`merge_and_unload()` перед прогоном. Для обучения сливать нельзя.

## 6. Сеть

CDN HuggingFace блокируется коварно: `200 OK` + корректный `Content-Length`,
а тело не идёт (0 байт за 90 с). Мы наблюдали ровно это — оба `snapshot_download`
висли. Рабочее решение: ручная укладка файлов в `checkpoints/baseline_qwen35_2b/`
(через зеркало hf-mirror.com сработало на 27 MB/s) + `HF_HUB_OFFLINE=1` +
локальные пути (`local_files_only=True`) везде.

## 7. Диагностика за три минуты

Прежде чем оптимизировать: замерить (а) bf16 GEMM 4096³ (десятки TFLOP/s =
карта здорова), (б) стоимость запуска ядра `x.add_(1)` ×2000 (~5 мкс норма),
(в) зависимость времени шага от батча: плоско → узкое место в хосте (графы,
батчинг), линейно → в GPU. См. `tools/benchmark_canvases.py` как основу.

## 8. Стартовый рецепт (применён в `tools/train_spatial.py`)

```yaml
precision: bfloat16
max_prompt_tokens: 256     # по измеренному p100 корпуса
max_code_tokens: 768       # p100=565 + запас
lr: 2.0e-4
warmup_steps: 30
lora: { r: 16, alpha: 32, dropout: 0.05, target_modules: [q_proj, k_proj, v_proj, o_proj] }
max_vram_gb: 14.0          # логируется и маркируется на каждом шаге
```

Важно: без LoRA замороженный бэкбон не перебивает привычку отвечать прозой
(у них: 750 батчей без адаптера — лосс застрял 1.81, 0% компиляций; с LoRA —
0.013 и 100% за 500 батчей). Наша архитектура это учитывает: адаптер +
канвас обучаются всегда вместе.

## 9. Мелочи

- Ключи конфига, которые никто не читает: наши `configs/*.yaml` —
  декларативные спецификации, авторитетны аргументы CLI; не доверять ключу без
  грепа по коду.
- Валидация на том же генераторе, что кормил обучение, честно показывала 100 %
  при полном мусоре на живой фразе. Отложенный набор написан руками
  (`optional_data/data/heldout_eval.jsonl`) — используется только для оценки.
- «Компилируется» ≠ «правильно»: конус вместо фланца компилируется. Поэтому
  метрика — bbox-ошибка ≤ 15 % против ожидаемых размеров, а не просто rc=0.
- Дообучение поверх чекпоинта честнее заменять чистым прогоном от нулевой
  точки: короткие прогоны стоят минуты, сравнение остаётся корректным
  (соответствует нашему контракту zero point).
