# Диагностика [B]: откуда берётся плохой габарит wire

**Дата:** 2026-10-30 (ночь на 31.10) · **Слой:** `wire` · **Веса:** `checkpoints/wire`
**Важно:** по разбору E7-a (`docs/E7A_V15_CHECKPOINT_LOSS.md`) это **веса v14**
(compile 16/42), а не v15. Прогон остаётся базой сравнения; после восстановления
весов v15 диагностику надо повторить.

## Как устроен эксперимент

Один чекпойнт, одни и те же строки, меняется только блок `[SPECS]` в промпте
(`tools/evaluate_generation.py --specs-mode`, код — `src/runtime/eval_specs.py`):

| режим | что в блоке | зачем |
|---|---|---|
| `auto` | `bbox` из `expected_bbox_mm`, если строка его несёт (oracle); иначе догадка минера | «идеальный масштаб» — верхняя граница |
| `mined` | всегда догадка минера по тексту | реальный путь пользователя |
| `none` | блока нет вообще (канвас всё равно получает bbox минера) | контроль: смотрит ли модель на блок |

Прогон: `tools/wsl_diag_wire_scale.sh wire` (WSL, отвязанно), сводка —
`tools/summarize_eval_modes.py` (полная версия — `runs/diag_wire_scale/REPORT.md`,
каталог в git не входит). Сырые прогоны: `data/processed/diag_wire_scale/`.

## Результаты

42 общих held-out строки:

| режим | compile | watertight | bbox ≤15 % | медиана err | медиана факт/эталон |
|---|---|---|---|---|---|
| auto | 16/42 | 16 | 6/16 | 0.818 | 1.00 |
| none | **0/42** | 0 | 0/0 | — | — |

4 wire-conv строки (`conv_gt_wire_*`, в тексте нет ни одной цифры — масштаб есть
только в oracle-блоке):

| режим | compile | bbox ≤15 % | медиана err | медиана факт/эталон |
|---|---|---|---|---|
| auto | 3/4 | 0/3 | 0.817 | **1.08** |
| mined | 3/4 | 0/3 | 1.301 | **2.30** |
| none | 1/4 | 0/1 | 1.428 | 2.43 |

## Что это значит

1. **Блок `[SPECS]` — не только масштаб, а часть формата запроса.** Без него
   wire-слой не компилируется вообще (0/42): модель обучена на «текст + блок +
   `<|spatial_wire|>`» и без блока уходит в чужое распределение. Поэтому контраст
   «auto vs none» ничего не говорит о масштабе — только о формате.
2. **Канал масштаба на wire работает.** На строках без цифр в тексте oracle-блок
   даёт медианный коэффициент «факт/эталон» **1.08** (ошибка +8 %), а догадка
   минера (по умолчанию `[100, 100, 100]`) — **2.30** (перебор в 2.3 раза).
   То есть модель слушает `bbox:` и честно масштабирует конструкцию.
3. **Габарит всё равно мимо порога 15 %** даже с oracle-блоком (0/3 на conv-строках,
   6/16 на общих): ошибка сидит не в общем масштабе, а в **пропорциях отдельных
   осей** (медиана err 0.82 при медиане отношения 1.08 — одна ось систематически
   «не та», например высота фермы против пролёта). Это уже задача геометрии
   wire-генераторов/данных, а не `[SPECS]`.
4. **Минер — измеримая потеря.** На безразмерных промптах он отдаёт дефолт
   `[100,100,100]` и добавляет +1.2 к коэффициенту габарита (2.30 против 1.08).
   Дешёвое улучшение: для wire-промптов без цифр выводить bbox из **скелета**
   (как в `wire_families_gen`: скелет + 2r), а не из `DEFAULT_BBOX`.

## Следующие шаги

1. Повторить этот же прогон на восстановленных весах v15 (задача E7-a) — цифры
   выше относятся к v14.
2. Добавить режим `--specs-mode skeleton` (bbox из аналитического скелета) и
   сравнить с `mined` на `heldout_conv_gt.jsonl` — это прямая проверка пункта 4.
3. Порог «wire bbox ≤15 %» пока недостижим по причинам пропорций; в отчётах
   полезнее смотреть медиану «факт/эталон» отдельно от медианы err.
