# План развития: композиция обученных Canvas для сложных сборок

## Статус документа

Это предложение по дальнейшему развитию OmniCraft-LM. Описанная составная архитектура **не является текущей реализацией**. Она предназначена для этапа после независимого обучения и проверки базовых Spatial Canvas.

## Краткий вывод

Отдельные Canvas можно и целесообразно сначала обучить в текущей архитектуре, а затем использовать как предварительно обученных геометрических экспертов:

```text
Обученные Voxel / Wire / Sketch / BRep Canvas
                        ↓
              CompositeAssemblyCanvas
                        ↓
                 сложная сборка
```

Переобучать базовые Canvas с нуля не обязательно. Потребуется дополнительное обучение планировщика компонентов, сборочного агрегатора и, возможно, небольшой совместный fine-tuning.

---

## 1. Что сохраняется после отдельного обучения

Каждый тип геометрии имеет изолированный обучаемый путь:

```text
ScaleMLP
   ↓
InProjector
   ↓
Canvas
   ↓
OutProjector
   ↓
LoRA соответствующего слоя
```

Артефакты должны храниться раздельно:

```text
checkpoints/
├── voxel/
├── wire/
├── sketch/
├── brep/
└── assembly/
```

В дальнейшем веса можно загрузить в составную систему и использовать как начальное состояние экспертов. Это позволяет сохранить уже приобретённые навыки обработки отдельных классов геометрии.

---

## 2. Рекомендуемый порядок развития

### Этап 1. Независимое обучение Canvas

Каждый Canvas сначала обучается решать ограниченную задачу:

```text
VoxelCanvas    → корпуса, полости, булевы операции
WireCanvas     → рамы, фермы, балки и стержни
SketchCanvas   → профили, фланцы, шестерни и экструзии
BRepCanvas     → точные поверхности, грани и рёбра
AssemblyCanvas → трансформации и структура сборки
```

Преимущества такого подхода:

- проще готовить датасеты;
- легче диагностировать ошибки;
- ниже требования к VRAM;
- неисправность одного Canvas не портит остальные;
- checkpoints можно тестировать и версионировать независимо.

### Этап 2. Фиксация и заморозка экспертов

После обучения Canvas переводятся в режим инференса и временно замораживаются:

```python
canvas.eval()
for parameter in canvas.parameters():
    parameter.requires_grad = False
```

На следующем этапе они рассматриваются как готовые геометрические эксперты:

```text
Voxel expert  ─┐
Wire expert   ─┤
Sketch expert ─┼→ замороженные модули
BRep expert   ─┘
```

### Этап 3. Component Planner

Необходимо добавить планировщик, который разбивает запрос на компоненты и назначает каждому компоненту подходящий Canvas.

Пример:

```text
«Создай редуктор»
        ↓
1. Корпус       → voxel
2. Крышка       → voxel
3. Шестерня A   → sketch
4. Шестерня B   → sketch
5. Вал A        → brep
6. Вал B        → brep
```

На первом этапе Planner может быть детерминированным и выдавать структурированный JSON:

```json
{
  "components": [
    {
      "name": "housing",
      "canvas": "voxel",
      "bbox": [120, 80, 60]
    },
    {
      "name": "gear_1",
      "canvas": "sketch",
      "bbox": [40, 40, 12]
    }
  ]
}
```

Это позволит проверить составную архитектуру до обучения нейросетевого Planner.

### Этап 4. Агрегатор компонентов

Обученные Canvas возвращают представления компонентов:

```text
housing → [512]
gear_1  → [512]
gear_2  → [512]
shaft   → [512]
```

Они собираются в общий тензор:

```text
[B, N_components, 512]
```

Расширенный AssemblyCanvas или новый `CompositeAssemblyCanvas` должен учитывать:

- латентные признаки компонентов;
- размеры компонентов;
- предполагаемые трансформации;
- связи и сопряжения;
- маску существующих деталей.

Предлагаемый контракт:

```text
Component latents
[B, N, 512]
       +
SE(3) transforms
[B, N, 4, 4]
       +
Relation graph
[B, N, N]
       +
Component mask
[B, N]
       ↓
CompositeAssemblyCanvas
       ↓
Assembly latent
[B, 512]
```

### Этап 5. Обучение сборочного уровня

Сначала геометрические эксперты остаются замороженными:

```text
VoxelCanvas             frozen
WireCanvas              frozen
SketchCanvas            frozen
BRepCanvas              frozen

Component Planner       trainable
CompositeAssemblyCanvas trainable
Assembly OutProjector   trainable
Assembly LoRA           trainable
```

Это позволяет научить сборочную систему использовать готовые представления, не разрушая навыки отдельных Canvas.

### Этап 6. Осторожный совместный fine-tuning

После стабилизации сборочного уровня можно выборочно разморозить:

- последние слои Canvas;
- проекторы;
- LoRA-адаптеры;
- fusion/aggregation layers.

Пример относительных learning rate:

```text
CompositeAssemblyCanvas: 1e-4
Projectors:              1e-5
Existing Canvas:         1e-6
```

Совместный fine-tuning не является обязательным. Если замороженные эксперты дают подходящие признаки, безопаснее сохранить их неизменными.

## 3. Предлагаемый вычислительный поток

Canvas компонентов лучше запускать независимо или параллельно, а не соединять в прямую цепочку.

Нежелательный вариант:

```text
VoxelCanvas → SketchCanvas → BRepCanvas → AssemblyCanvas
```

Эти Canvas описывают разные виды геометрии, а не последовательные стадии одной обработки.

Рекомендуемый вариант:

```text
                  ┌→ Canvas детали 1 ─┐
Qwen → Planner ───┼→ Canvas детали 2 ─┼→ CompositeAssemblyCanvas → Qwen
                  └→ Canvas детали N ─┘
```

Внутри одного этапа prefill это может выглядеть так:

```text
Запрос пользователя
        ↓
Qwen: слои 0–11
        ↓
Component Planner
        ↓
параллельная обработка компонентов
        ↓
CompositeAssemblyCanvas
        ↓
Assembly OutProjector: 512 → 2048
        ↓
Residual Injection
        ↓
Qwen: слои 12–23
        ↓
генерация CAD-кода
```

Для пользователя это остаётся одним запросом и одной генерацией. После неё внешний CAD-цикл должен проверить размеры, сопряжения и столкновения.

---

## 4. Важная роль выхода до OutProjector

Текущий независимый путь заканчивается преобразованием результата Canvas в пространство Qwen:

```text
Canvas 512
    ↓
OutProjector
    ↓
Qwen 2048
```

Для будущей композиции предпочтительно использовать представление **до OutProjector**:

```text
Canvas output: [B, 512]
```

Составная схема должна применять общий Assembly OutProjector только после объединения компонентов:

```text
Canvas детали → latent 512 ─┐
Canvas детали → latent 512 ─┼→ CompositeAssemblyCanvas → latent 512
Canvas детали → latent 512 ─┘                              ↓
                                                   OutProjector
                                                        ↓
                                                   Qwen 2048
```

Это уменьшает размерность промежуточных данных и сохраняет пространственные признаки в общем формате Canvas.

---

## 5. Что важно сохранить уже сейчас

### 5.1. Единая размерность

Все Canvas должны возвращать латентный вектор:

```text
[B, 512]
```

Это базовый контракт для будущего агрегатора.

### 5.2. Раздельные checkpoints

Для каждого эксперта необходимо сохранять:

- `ScaleMLP`;
- `InProjector`;
- сам Canvas;
- `OutProjector`;
- LoRA-адаптер;
- версию архитектуры;
- версию конфигурации;
- идентификатор и хеш датасета;
- метрики валидации.

### 5.3. Стабильный программный интерфейс

Желательно закрепить отдельный контракт получения внутреннего представления:

```python
Canvas input -> Canvas latent [B, 512]
```

Sketch, BRep и Assembly Canvas принимают структурированные входы, а не только `z_in`. Это различие следует явно отразить в будущем интерфейсе композиции.

### 5.4. Метаданные сопряжений

В датасеты отдельных деталей полезно уже сейчас включать сведения об интерфейсах:

```json
{
  "object_class": "gear",
  "canvas": "sketch",
  "bbox": [40, 40, 12],
  "interfaces": [
    {
      "type": "shaft_hole",
      "diameter": 8,
      "axis": "z"
    }
  ]
}
```

Особенно важны:

- отверстия под валы;
- плоскости крепления;
- оси вращения;
- точки болтов;
- входные и выходные порты;
- допустимые степени свободы;
- посадки и зазоры;
- базовые поверхности.

Без этих данных Canvas может хорошо описывать отдельную деталь, но сборочному уровню будет сложно понять, как соединять компоненты.

### 5.5. Версионирование латентного пространства

Латентный вектор `[512]` не имеет фиксированного человеческого смысла. После повторного обучения внутреннее пространство Canvas может измениться.

Поэтому `CompositeAssemblyCanvas` должен быть привязан к конкретным версиям checkpoints экспертов. Замена эксперта требует проверки совместимости или дополнительного fine-tuning агрегатора.

---

## 6. Дополнительные обучающие цели

Главный риск состоит в том, что отдельный Canvas может научиться выдавать полезную подсказку непосредственно для Qwen, но его внутренний латент не обязательно окажется удобным для другого Canvas.

```text
Canvas → Qwen
```

может работать хорошо, а:

```text
Canvas → CompositeAssemblyCanvas
```

— значительно хуже.

Для снижения риска к независимому обучению Canvas полезно добавить вспомогательные задачи:

- предсказание BBox;
- классификация детали;
- оси и плоскости симметрии;
- точки, оси и поверхности сопряжения;
- занимаемый объём;
- граф рёбер и связей;
- типы геометрических примитивов;
- ориентация локальной системы координат;
- технические зазоры и посадочные размеры.

Такие задачи сделают 512-мерное представление полезным не только для генерации кода, но и для последующей композиции.

---

## 7. Однопроходный и итеративный режимы

### Однопроходный нейросетевой режим

```text
Запрос → Planner → несколько Canvas → AssemblyCanvas → генерация кода
```

Он может выполняться за один prefill и пригоден для обучения.

### Итеративный инженерный режим

```text
План
  ↓
генерация деталей и сборки
  ↓
CAD-компиляция
  ↓
проверка столкновений и сопряжений
  ↓
исправление размеров или положения
  ↓
повторная проверка
```

Сложные сборки обычно требуют обратной связи, поэтому один нейросетевой проход должен формировать первоначальный проект, но не заменять CAD-валидацию.

Оптимальная итоговая система сочетает оба режима:

> Несколько Canvas за один prefill создают первоначальное представление сборки, после чего внешний CAD-контур проверяет геометрию и при необходимости инициирует исправление.

---

## 8. Какие новые компоненты потребуются

Для реализации составной архитектуры понадобятся:

1. `ComponentPlanner` — декомпозиция запроса.
2. Схема данных `AssemblyPlan`.
3. Список Canvas вместо одного поля `canvas` в `[SPECS]`.
4. Описание компонентов и их индивидуальных BBox.
5. `CompositeCanvasBundle` или аналогичный оркестратор.
6. `CompositeAssemblyCanvas` с входом `[B, N, 512]`.
7. Граф сопряжений `[B, N, N]`.
8. Маскирование переменного числа компонентов.
9. Функции потерь для трансформаций, сопряжений и коллизий.
10. Сборочный датасет с иерархией компонентов.
11. Верификатор сборок на реальном CAD-runtime.
12. Тесты обратной совместимости checkpoints.

---

## 9. Потребность в переобучении

### Не требуется

Не требуется обучать существующие Canvas с нуля. Их следует использовать как предварительно обученных экспертов.

### Требуется

Необходимо отдельно обучить:

- Component Planner;
- маршрутизацию компонентов;
- CompositeAssemblyCanvas;
- модель графа сопряжений;
- Assembly OutProjector;
- возможно, отдельный Assembly LoRA.

### Может потребоваться

После обучения сборочного слоя может понадобиться небольшой совместный fine-tuning проекторов и последних слоёв экспертов. Решение должно приниматься по результатам экспериментов с замороженными Canvas.

---

## 10. Рекомендуемый roadmap

```text
1. Независимое обучение Canvas
2. Проверка и фиксация checkpoints
3. Добавление метаданных сопряжений в датасеты
4. Заморозка обученных экспертов
5. Реализация детерминированного Component Planner
6. Реализация CompositeAssemblyCanvas
7. Обучение сборочного уровня
8. CAD-валидация сложных сборок
9. Нейросетевой Planner вместо детерминированного
10. При необходимости — осторожный совместный fine-tuning
```

## Итоговое решение

Сначала следует завершить независимое обучение Canvas на текущей архитектуре. После этого их можно использовать как готовые геометрические эксперты в иерархической системе сложных сборок.

Критически важно уже на текущем этапе:

- сохранять раздельные и версионированные checkpoints;
- поддерживать общий выход `[B, 512]` до `OutProjector`;
- собирать метаданные о сопряжениях;
- не привязывать будущий агрегатор к нестабильным версиям латентного пространства;
- рассматривать CAD-валидацию как обязательный внешний контур.

Такой порядок минимизирует риск потери уже обученных навыков и позволяет развивать сборочную архитектуру поверх стабильных модульных компонентов.
